## Task 1: GitHub Secrets

Created a repository secret:

`MY_SECRET_MESSAGE`

Location:

`Repository → Settings → Secrets and variables → Actions`

Used the secret in a workflow without exposing its actual value.

Example:

    - name: Check secret
      run: |
        if [ -n "${{ secrets.MY_SECRET_MESSAGE }}" ]; then
          echo "The secret is set: true"
        else
          echo "The secret is set: false"
        fi

Also tested printing the secret directly:

    echo "${{ secrets.MY_SECRET_MESSAGE }}"

GitHub masks the secret value in workflow logs, so the actual value is hidden.

### Why Should Secrets Never Be Printed in CI Logs?

Secrets should never be intentionally printed because CI logs can be viewed by people with access to the repository or workflow.

Exposing secrets can lead to:

- Unauthorized access
- Credential leakage
- Compromised services
- Security incidents

Secrets should only be used when required and should never be hardcoded in workflow files.

### Observation

GitHub automatically masks registered secret values in logs, but masking should not be treated as a reason to print secrets.

## Task 2: Use Secrets as Environment Variables

Passed the secret to a step using an environment variable.

    - name: Use secret
      env:
        SECRET_MESSAGE: ${{ secrets.MY_SECRET_MESSAGE }}
      run: |
        echo "Secret is available: $([ -n "$SECRET_MESSAGE" ] && echo true || echo false)"

The actual secret value was never hardcoded in the workflow.

Also created the following repository secrets for future Docker workflows:

- `DOCKER_USERNAME`
- `DOCKER_TOKEN`

These will be used later for Docker Hub authentication.

### Observation

Using environment variables keeps secret values separate from the workflow code and makes them easier to use in shell commands and tools.

## Task 3: Upload Artifacts

Created a file during the workflow and uploaded it as an artifact.

Example:

    - name: Generate test report
      run: |
        echo "Test Report" > test-report.txt
        echo "All tests passed" >> test-report.txt

    - name: Upload test report
      uses: actions/upload-artifact@v4
      with:
        name: test-report
        path: test-report.txt

After the workflow completed, the artifact was available in the workflow run under the **Artifacts** section and could be downloaded.

### Observation

Artifacts allow files generated during a workflow to be stored and accessed after the job finishes.

## Task 4: Download Artifacts Between Jobs

Created two jobs:

- Job 1 generates and uploads a file
- Job 2 downloads and uses the artifact

Example:

    jobs:
      create-artifact:
        runs-on: ubuntu-latest

        steps:
          - name: Create file
            run: echo "Generated by Job 1" > output.txt

          - name: Upload artifact
            uses: actions/upload-artifact@v4
            with:
              name: job-output
              path: output.txt

      use-artifact:
        needs: create-artifact
        runs-on: ubuntu-latest

        steps:
          - name: Download artifact
            uses: actions/download-artifact@v4
            with:
              name: job-output

          - name: Read artifact
            run: cat output.txt

### Observation

Job 2 successfully downloaded the file created by Job 1 and printed its contents.

### When Would You Use Artifacts in a Real Pipeline?

Artifacts are useful when one stage produces files that need to be stored or used later.

Examples:

- Test reports
- Build packages
- Logs
- Screenshots
- Compiled application files
- Deployment packages

They are especially useful when different jobs run on separate runners.

## Task 5: Run Real Tests in CI

Added a script from an earlier DevOps task to the `github-actions-practice` repository.

The workflow:

1. Checks out the repository
2. Installs required dependencies
3. Runs the script/test
4. Fails when the script exits with a non-zero status

Example:

    name: Run Tests

    on:
      push:
      pull_request:
      workflow_dispatch:

    jobs:
      test:
        runs-on: ubuntu-latest

        steps:
          - name: Checkout code
            uses: actions/checkout@v4

          - name: Run test script
            run: bash test.sh

### Observation

When the script completed successfully, the workflow passed.

I intentionally introduced an error into the script and pushed the change.

The workflow then failed because the script returned a non-zero exit code.

After fixing the script, the workflow passed again.

### CI Test Flow

    Code Push
        ↓
    Checkout Code
        ↓
    Run Script
        ↓
    Tests Pass → Green
    Tests Fail → Red

## Task 6: Caching

Added `actions/cache` to a workflow that uses dependencies.

Example:

    - name: Cache dependencies
      uses: actions/cache@v4
      with:
        path: ~/.cache
        key: ${{ runner.os }}-dependencies-${{ hashFiles('**/requirements.txt') }}

    - name: Install dependencies
      run: |
        # Install required dependencies here

The cache key is based on the operating system and dependency file.

If the dependency file changes, a new cache can be created.

### What Is Being Cached?

The cache stores reusable dependency-related files so that they do not need to be downloaded or generated again on every workflow run.

### Where Is It Stored?

The cache is stored by GitHub Actions and can be restored on future workflow runs when the cache key matches.

### Observation

The first workflow run may create the cache.

On later runs with the same cache key, the existing cache can be restored, reducing unnecessary dependency setup time.

## Key Takeaways

- GitHub Secrets are used to store sensitive values securely.
- Secrets should never be intentionally exposed in CI logs.
- Secrets can be passed to commands using environment variables.
- Artifacts preserve files generated during workflow execution.
- Artifacts can be shared between different jobs.
- CI can execute real scripts and tests automatically.
- A non-zero exit code normally causes a workflow step and job to fail.
- `actions/cache` can reduce repeated dependency setup time.
- Caching and artifacts solve different problems: caches improve performance, while artifacts preserve workflow outputs.
