
# Day 73: Introduction to Observability and Prometheus

## Overview

Infrastructure provisioning with Terraform, server configuration with Ansible, and application containerization with Docker help us deploy applications. However, deploying an application is only part of the job.

We also need to know whether the application is healthy, how much memory it consumes, whether requests are failing, and why an issue occurs.

This is where **observability** comes in.

In Day 73 of the #90DaysOfDevOps journey, the focus is on understanding the three pillars of observability, setting up Prometheus with Docker Compose, exploring PromQL, and monitoring a sample application.

## Objectives

- Understand observability and how it differs from traditional monitoring.
- Learn the three pillars: metrics, logs, and traces.
- Run Prometheus using Docker Compose.
- Configure Prometheus scrape targets.
- Understand metrics, labels, time series, and metric types.
- Execute PromQL queries.
- Explore Prometheus data storage and retention.
- Prepare the foundation for a complete observability stack.

## Task 1: Understanding Observability

### What is Observability?

Observability is the ability to understand the internal state of a system by examining the data it produces.

In a production environment, an application can fail for many reasons, including high resource consumption, database timeouts, network problems, or errors between services.

Observability helps us investigate these issues using metrics, logs, and traces.

### Observability vs Traditional Monitoring

| Traditional Monitoring | Observability |
|---|---|
| Focuses on detecting known problems. | Helps investigate both known and unexpected problems. |
| Uses alerts, thresholds, and predefined checks. | Uses queries and correlated telemetry data. |
| Answers: What is wrong? | Helps answer: Why is it wrong, and where did it happen? |
| Example: CPU usage exceeds 90%. | Example: Investigating whether high CPU usage is related to a traffic spike or a slow application operation. |

Monitoring and observability complement each other. Monitoring detects problems, while observability helps us investigate and understand them.

### The Three Pillars of Observability

#### 1. Metrics

Metrics are numerical measurements collected over time.

Examples:
- CPU utilization
- Memory usage
- HTTP request count
- Application error rate
- Request duration

Common tools:
- Prometheus
- Datadog
- AWS CloudWatch

**Example:** If the application error rate suddenly increases, metrics help us identify when the problem started and how severe it is.

#### 2. Logs

Logs are timestamped records of events generated by applications and infrastructure.

Examples:
- Application startup messages
- Database connection failures
- Authentication errors
- Exception stack traces

Common tools:
- Grafana Loki
- ELK Stack
- Fluentd

**Example:** If an API starts returning errors, application logs may reveal that the database connection timed out.

#### 3. Traces

Traces show the journey of a request as it travels through different components or services.

Common tools:
- OpenTelemetry
- Jaeger
- Zipkin

**Example:** A request may pass through an API gateway, an application service, and a database. A distributed trace can help identify which operation introduced the delay.

### Why Do DevOps Engineers Need All Three?

Consider an application where the `/api/users` endpoint becomes slow.

- **Metrics** show an increase in request latency and errors.
- **Logs** reveal database timeout messages.
- **Traces** identify the database call that is taking too long.

Together, these signals provide a clearer picture than any one of them alone.

## Task 2: Setting Up Prometheus with Docker

### What is Prometheus?

Prometheus is an open-source monitoring and metrics collection system. It collects time-series metrics from configured targets and provides PromQL for querying those metrics.

Prometheus generally uses a **pull-based model**. It periodically requests metrics from configured HTTP endpoints.

### Step 1: Create the Project Directory

For this practical, Docker Desktop is used on Windows.

```bash
mkdir observability-stack
cd observability-stack
```

The directory structure is:

```text
observability-stack/
├── docker-compose.yml
└── prometheus.yml
```

### Step 2: Create prometheus.yml

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: "prometheus"
    static_configs:
      - targets: ["prometheus:9090"]
```

Explanation:

- `scrape_interval`: Prometheus collects metrics every 15 seconds by default.
- `evaluation_interval`: Prometheus evaluates configured recording and alerting rules at this interval.
- `job_name`: Identifies the scrape job.
- `targets`: Specifies the endpoint from which metrics are collected.

**Why use `prometheus:9090` instead of `localhost:9090`?**

The Compose service name resolves to the Prometheus container on the Docker network. This avoids confusion between the Windows host and the container's own network namespace.

### Step 3: Create docker-compose.yml

```yaml
services:
  prometheus:
    image: prom/prometheus:latest
    container_name: prometheus
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
      - prometheus_data:/prometheus
    command:
      - "--config.file=/etc/prometheus/prometheus.yml"
    restart: unless-stopped

volumes:
  prometheus_data:
```

### Understanding the Configuration

| Configuration | Purpose |
|---|---|
| `image` | Uses the official Prometheus container image. |
| `container_name` | Assigns the container the name `prometheus`. |
| `9090:9090` | Maps port 9090 on the Windows host to port 9090 in the container. |
| `./prometheus.yml:...` | Mounts the local configuration file into the container. |
| `prometheus_data:/prometheus` | Persists Prometheus time-series data in a named Docker volume. |
| `restart: unless-stopped` | Restarts the container after a failure or Docker restart unless it was explicitly stopped. |

**Do we need to specify the full Windows path?**

No. Since `prometheus.yml` is in the same directory as `docker-compose.yml`, the relative path `./prometheus.yml` is sufficient.

For example, the files could be stored in:

```text
C:\Users\YourUsername\Desktop\observability-stack\
```

Docker Compose resolves `./prometheus.yml` relative to the Compose project directory.

The named volume `prometheus_data` is managed by Docker. It is not a Windows path that we need to write ourselves.

### Step 4: Start Prometheus

Ensure Docker Desktop is running, then execute:

```bash
docker compose config
docker compose up -d
docker compose ps
```

Check the container logs if needed:

```bash
docker logs prometheus
```

### Step 5: Open the Prometheus UI

Open the following address in your browser:

http://localhost:9090

Navigate to:

**Status → Targets**

The `prometheus` target should eventually show the state `UP`.

You can also check the graph page:

http://localhost:9090/graph

Enter this query:

```promql
up
```

A value of `1` indicates that the scrape target is reachable and its scrape succeeded. A value of `0` indicates a failed scrape.

## Task 3: Understanding Prometheus Concepts

### 1. Scrape Targets

A scrape target is an endpoint from which Prometheus collects metrics.

For example:

```yaml
- job_name: "prometheus"
  static_configs:
    - targets: ["prometheus:9090"]
```

Prometheus periodically requests the metrics endpoint exposed by the target.

### 2. Metric Types

#### Counter

A counter is a cumulative value that increases as events occur. It can reset when the instrumented process restarts.

Examples:
- Total HTTP requests received
- Total failed requests
- Total jobs processed

A counter is useful for calculating event rates with `rate()`.

#### Gauge

A gauge represents a value that can increase or decrease.

Examples:
- Current memory usage
- Number of active connections
- Current queue size

A gauge is useful when we need to know the current state of a system.

#### Histogram

A histogram samples observations and groups them into configurable buckets. It also tracks the total number of observations and their sum.

Example:
- Distribution of HTTP request durations.

A histogram can help answer questions such as how many requests completed within 100 milliseconds.

#### Summary

A summary tracks observations and can calculate configured quantiles on the instrumented application side. It also tracks the count and sum of observations.

Histograms are often more suitable when latency needs to be aggregated across multiple instances.

### 3. Labels

Labels are key-value pairs that add dimensions to a metric.

Example:

```promql
http_requests_total{method="GET", status="200"}
```

Here, `method` and `status` distinguish the requests represented by the metric.

Be careful with labels that have many possible values, such as user IDs or request IDs, because they can create excessive time series.

### 4. Time Series

A time series is identified by a metric name and its complete set of labels.

For example:

```promql
http_requests_total{method="GET", status="200"}
```

A series records the value of that particular metric and label combination over time.

### Counter vs Gauge: Real-World Example

| Counter | Gauge |
|---|---|
| Total requests received by an API. | Number of requests currently being processed. |
| Increases as requests arrive. | Can increase or decrease. |
| Commonly queried with `rate()`. | Usually queried directly or aggregated. |

A counter tells us how many events have occurred, while a gauge tells us the current value of something.

### Explore Prometheus Metrics

Run these queries in the Prometheus graph UI.

#### Count the currently exposed metric series

```promql
count({__name__=~".+"})
```

This counts the matching time series currently returned by the selector, not every metric ever collected.

#### Prometheus process memory usage

```promql
process_resident_memory_bytes
```

This reports resident memory in bytes. It may return more than one series depending on the labels.

#### Total HTTP requests to Prometheus

```promql
prometheus_http_requests_total
```

This is a counter representing the total number of HTTP requests handled by Prometheus, separated by labels.

#### Requests handled by a specific endpoint

```promql
prometheus_http_requests_total{handler="/api/v1/query"}
```

This filters the request counter to the matching handler label. The exact labels and matching series depend on the Prometheus version and available instrumentation.

## Task 4: Learning PromQL Basics

PromQL stands for Prometheus Query Language. It is used to select, calculate, aggregate, and analyze time-series data.

### 1. Instant Vector

```promql
up
```

Returns the most recent sample for each matching target series.

A value of `1` means the last scrape succeeded; `0` means the last scrape failed.

### 2. Range Vector

```promql
prometheus_http_requests_total[5m]
```

Returns the samples for matching series over the last five minutes.

Range vectors are used by functions such as `rate()`.

### 3. Rate

```promql
rate(prometheus_http_requests_total[5m])
```

Calculates the average per-second increase of the counter over the last five minutes.

Counters increase cumulatively, so `rate()` helps us understand how quickly events are occurring.

### 4. Aggregation

```promql
sum(rate(prometheus_http_requests_total[5m]))
```

Calculates the total per-second request rate across the matching series.

For counters, apply `rate()` before aggregation so counter resets can be handled for each series.

### 5. Filter by Label

```promql
prometheus_http_requests_total{code="200"}
```

Selects matching request series with HTTP status code 200, if that label is available.

```promql
prometheus_http_requests_total{code!="200"}
```

Selects series where the `code` label is not equal to `200`. If the label is absent, Prometheus label matching semantics also affect whether a series matches.

### 6. Convert Bytes to Megabytes

```promql
process_resident_memory_bytes / 1024 / 1024
```

Converts the process resident memory value from bytes to mebibytes (MiB).

### 7. Top-K

```promql
topk(5, prometheus_http_requests_total)
```

Returns up to five series with the highest counter values. This ranks the current counter values, not necessarily the highest request rates.

### Challenge: Rate of Non-200 HTTP Requests

The task asks for the per-second rate of non-200 requests over the last five minutes.

```promql
sum(rate(prometheus_http_requests_total{code!="200"}[5m]))
```

This query:
1. Filters the request counter to non-200 status codes.
2. Calculates the per-second rate over five minutes.
3. Sums the resulting rates across matching series.

If the `code` label is not present in your Prometheus version or instrumentation, inspect the available labels and adapt the query.

### Five Queries to Document

| Query | What it tells us |
|---|---|
| `up` | Whether each target's latest scrape succeeded. |
| `process_resident_memory_bytes` | Resident memory used by the instrumented process. |
| `prometheus_http_requests_total` | Cumulative HTTP requests handled by Prometheus. |
| `rate(prometheus_http_requests_total[5m])` | Average request rate per second over five minutes. |
| `sum(rate(prometheus_http_requests_total{code!="200"}[5m]))` | Aggregate rate of matching non-200 requests, if the `code` label exists. |

Document the actual results from your Prometheus UI rather than assuming every query will return data.

## Task 5: Add a Sample Application as a Scrape Target

Prometheus needs a target that exposes metrics in a format it can scrape.

The learning task uses a sample Notes application. Before assuming it exposes metrics, verify that the application has a Prometheus-compatible metrics endpoint.

### Update docker-compose.yml

Add the sample application service:

```yaml
  notes-app:
    image: trainwithshubham/notes-app:latest
    container_name: notes-app
    ports:
      - "8000:8000"
    restart: unless-stopped
```

Keep this service under the existing top-level `services:` key, alongside Prometheus.

### Update prometheus.yml

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: "prometheus"
    static_configs:
      - targets: ["prometheus:9090"]

  - job_name: "notes-app"
    metrics_path: /metrics
    static_configs:
      - targets: ["notes-app:8000"]
```

The default Prometheus scrape path is `/metrics`, so `metrics_path` can be omitted if the application exposes metrics there.

**Important:** Do not assume the Notes app exposes `/metrics` simply because it runs on port 8000. Confirm its documentation or inspect its response first. If it does not expose Prometheus metrics, Prometheus will report the target as `DOWN` or fail to parse the response. You will need a metrics-enabled application or exporter to complete this part.

### Restart the Stack

```bash
docker compose up -d
docker compose ps
```

Check the targets page:

http://localhost:9090/targets

Generate some application traffic:

```bash
curl http://localhost:8000
curl http://localhost:8000
curl http://localhost:8000
```

Traffic generation and metrics scraping are different things: sending requests to the application does not automatically make those requests visible in Prometheus unless the application exposes relevant metrics.

## Task 6: Data Retention and Storage

### How Prometheus Stores Data

Prometheus stores scraped metrics in its local time-series database (TSDB).

By default, Prometheus retains data for 15 days, subject to storage limits and configuration. Data can be removed earlier if a configured retention-size limit is reached.

### Check Prometheus Storage Usage

```bash
docker exec prometheus du -sh /prometheus
```

This command checks the size of the data directory inside the container. The exact reported size depends on the metrics collected and the time Prometheus has been running.

### Configure Retention

Add the following arguments to the Prometheus service in `docker-compose.yml`:

```yaml
command:
  - "--config.file=/etc/prometheus/prometheus.yml"
  - "--storage.tsdb.retention.time=30d"
  - "--storage.tsdb.retention.size=1GB"
```

These settings configure a 30-day time retention period and a 1 GB size limit.

The retention size is a limit on Prometheus TSDB storage, not a guarantee that all data will be kept for 30 days. When the size limit is reached, Prometheus removes older data to stay within the configured limit.

Recreate the container after changing the configuration:

```bash
docker compose up -d
```

Check **Status → TSDB Status** in the Prometheus UI.

### Why Is a Persistent Volume Important?

Without persistent storage, deleting and recreating a container can cause its writable container filesystem and locally stored metrics to be lost.

The named volume:

```yaml
volumes:
  - prometheus_data:/prometheus
```

allows the data to survive normal container recreation.

A named volume does not protect against every failure, such as accidental volume deletion or disk failure. Important monitoring data may also require a backup and recovery strategy.

### What Happens When Retention Is Exceeded?

Prometheus removes older data according to its configured retention limits. This prevents its local TSDB from growing indefinitely.

The retention time and size settings work together, and the storage limit can cause older data to be deleted before the time limit is reached.

## Troubleshooting

### Prometheus Container Is Not Running

```bash
docker compose ps
docker logs prometheus
```

Check the logs for configuration errors, permission problems, or port conflicts.

### Port 9090 Is Already in Use

Another process may already be using port 9090. You can change the host-side port mapping:

```yaml
ports:
  - "9091:9090"
```

Then open:

http://localhost:9091

The container continues listening on port 9090 internally.

### A Target Shows DOWN

Check the following:

1. Is the target container running?
2. Is the target port correct?
3. Are both services on the same Docker network?
4. Does the target expose a valid metrics endpoint?
5. Can Prometheus resolve the Compose service name?
6. What error is displayed in the target's scrape details?

### Configuration Changes Are Not Reflected

Check the configuration:

```bash
docker compose config
```

Recreate or restart the service after updating `prometheus.yml`:

```bash
docker compose up -d
```

Prometheus can also reload its configuration through its lifecycle endpoint if lifecycle support has been enabled. Do not assume that configuration changes are automatically reloaded.

## Key Learnings

- Observability helps us investigate the internal state of a system using metrics, logs, and traces.
- Prometheus collects metrics through a pull-based scraping model.
- Scrape targets and the `up` metric help us determine whether metrics collection is working.
- Counters represent cumulative events, while gauges represent values that can increase or decrease.
- PromQL allows us to filter, aggregate, and analyze time-series data.
- Docker Compose makes it straightforward to run Prometheus locally on Windows with Docker Desktop.
- Relative bind-mount paths work well for project configuration files, while named volumes persist monitoring data.
- Retention settings help control how long metrics are stored and how much disk space they consume.

## Conclusion

Day 73 introduces the fundamentals of observability and provides the first building block of the monitoring stack: Prometheus.

With Prometheus running and its scrape targets configured, the next step is to expand monitoring beyond Prometheus itself and collect useful metrics from the host, containers, and applications.

**The goal is not just to know that a system is running, but to gather the data needed to understand its behavior and troubleshoot problems.**
