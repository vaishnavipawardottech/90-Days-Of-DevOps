## Task 1: Multi-Job Workflow

Created `.github/workflows/multi-job.yml` with three jobs:

- `build` – prints "Building the app"
- `test` – prints "Running tests"
- `deploy` – prints "Deploying"

The jobs were connected using `needs:` so that each job waits for the previous job to complete successfully.

    jobs:
      build:
        runs-on: ubuntu-latest
        steps:
          - run: echo "Building the app"

      test:
        needs: build
        runs-on: ubuntu-latest
        steps:
          - run: echo "Running tests"

      deploy:
        needs: test
        runs-on: ubuntu-latest
        steps:
          - run: echo "Deploying"

### Observation

The workflow graph shows:

`build → test → deploy`

`test` starts only after `build` succeeds, and `deploy` starts only after `test` succeeds.

### Key Point

`needs:` is used to create dependencies between jobs.

## Task 2: Environment Variables

Used environment variables at three different levels:

### Workflow Level

Available to all jobs and steps.

    env:
      APP_NAME: myapp

### Job Level

Available to all steps inside that job.

    jobs:
      example:
        env:
          ENVIRONMENT: staging

### Step Level

Available only inside that particular step.

    - name: Show variables
      env:
        VERSION: 1.0.0
      run: |
        echo "App: $APP_NAME"
        echo "Environment: $ENVIRONMENT"
        echo "Version: $VERSION"

Also used GitHub context variables:

    echo "Commit SHA: ${{ github.sha }}"
    echo "Triggered by: ${{ github.actor }}"

### Observation

Environment variables make workflow configuration easier to reuse, while GitHub context variables provide information about the current workflow run.

## Task 3: Job Outputs

Created one job that generates today's date and exposes it as an output.

    jobs:
      generate-date:
        runs-on: ubuntu-latest
        outputs:
          date: ${{ steps.date.outputs.date }}
        steps:
          - id: date
            run: echo "date=$(date)" >> $GITHUB_OUTPUT

      use-date:
        needs: generate-date
        runs-on: ubuntu-latest
        steps:
          - run: echo "Date from previous job: ${{ needs.generate-date.outputs.date }}"

### Observation

The second job successfully received the value generated by the first job.

### Why Pass Outputs Between Jobs?

Jobs normally run independently and have separate environments. Job outputs allow one job to pass important data to another job.

For example:

- Build job → generated version
- Test job → test result
- Deployment job → deployment information

### Key Point

`outputs:` defines data produced by a job.

`${{ needs.<job>.outputs.<name> }}` reads that data from another job.

## Task 4: Conditionals

Used conditions to control when steps and jobs execute.

### Run Step Only on Main

    - name: Main branch step
      if: github.ref == 'refs/heads/main'
      run: echo "Running on main branch"

### Run Step When Previous Step Fails

    - name: Failing step
      run: exit 1

    - name: Run after failure
      if: failure()
      run: echo "Previous step failed"

### Run Job Only on Push

    push-only:
      if: github.event_name == 'push'
      runs-on: ubuntu-latest
      steps:
        - run: echo "This job runs only for push events"

### Continue on Error

    - name: Allowed failure
      continue-on-error: true
      run: exit 1

### Observation

`continue-on-error: true` allows the step to fail without causing the overall job to fail.

This is useful when a step is optional or its failure should not stop the rest of the workflow.

### Key Point

Conditions allow workflows to make decisions instead of always executing every step and job.

## Task 5: Putting It Together

Created `.github/workflows/smart-pipeline.yml`.

The workflow:

- Runs on push to any branch
- Runs `lint` and `test` jobs in parallel
- Runs `summary` after both jobs complete
- Identifies whether the push is to `main` or a feature branch
- Prints the commit message

    name: Smart Pipeline

    on:
      push:

    jobs:
      lint:
        runs-on: ubuntu-latest
        steps:
          - run: echo "Running lint checks"

      test:
        runs-on: ubuntu-latest
        steps:
          - run: echo "Running tests"

      summary:
        needs: [lint, test]
        runs-on: ubuntu-latest
        steps:
          - name: Branch information
            run: |
              if [ "${{ github.ref }}" = "refs/heads/main" ]; then
                echo "This is a main branch push"
              else
                echo "This is a feature branch push"
              fi

          - name: Commit message
            run: echo "Commit message: ${{ github.event.commits[0].message }}"

### Observation

The `lint` and `test` jobs run independently and can execute in parallel.

The `summary` job waits for both jobs because of:

    needs: [lint, test]

This creates the following flow:

`lint ──┐`
`      ├──> summary`
`test ──┘`

## Important Concepts

### `needs:`

Defines a dependency between jobs.

    needs: build

The dependent job runs only after the required job completes successfully.

Multiple dependencies can be specified:

    needs: [lint, test]

### `outputs:`

Allows a job to expose a value that can be consumed by another job.

    outputs:
      date: ${{ steps.date.outputs.date }}

### `GITHUB_OUTPUT`

Used to create step outputs.

    echo "date=$(date)" >> $GITHUB_OUTPUT

### `if:`

Controls whether a step or job should execute.

Example:

    if: github.ref == 'refs/heads/main'

### `continue-on-error`

Allows a step to fail without failing the entire job.

---

## Key Takeaways

- Jobs can be connected using `needs:`.
- Independent jobs can run in parallel.
- Environment variables can be defined at workflow, job, or step level.
- GitHub context variables provide information about the workflow run.
- Job outputs allow data to be passed between jobs.
- `if:` controls conditional execution.
- `failure()` can be used to run steps after a failure.
- `continue-on-error` allows selected steps to fail without stopping the job.
- Combining these features allows more flexible and controlled CI/CD pipelines.
